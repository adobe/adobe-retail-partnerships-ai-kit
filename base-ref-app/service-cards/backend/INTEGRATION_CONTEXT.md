# Integration Context — Partner Ref App BFF

*Where the Adobe integration actually lives inside this backend surface.
This is the feature-less base app — nothing below exists yet; this card
records where it should go.*

---

## Where `partner_reference_id` Is Stored

- **Stored in:** `TODO — ASK PARTNER` / not yet created. No collection or field
  for `partner_reference_id` exists. The only existing Mongo collection is
  `partners_ref_app_partners` (`bff/src/db/partnerStore.ts`), which holds
  partner *login* records (`id`, `displayName`, `maxClaims`) —
  **not** subscription/claim state. A new collection (e.g.
  `partners_ref_app_subscriptions`, keyed by `(userId, offerId)`) is needed.
- **Generated by:** not yet implemented — per
  [`../../../manual/methodology/verification.md`](../../../manual/methodology/verification.md) rule /
  [`../../../skills/implement-feature/SKILL.md`](../../../skills/implement-feature/SKILL.md),
  the backend must generate + store it server-side on first claim, keyed by
  `(userId, offerId)`, and never accept one from the client.
- **Format:** `TODO — ASK PARTNER`. This bundled base app has no existing
  customer/order ID convention to reuse (it is feature-less — no orders exist
  yet). A real partner very likely has one; check their codebase first. Absent
  an answer, `implement-feature` falls back to a fresh UUID as an illustrative
  default only (see
  [`../../../knowledgebase/integration-patterns/idempotency.md`](../../../knowledgebase/integration-patterns/idempotency.md)) —
  not a format to assume is required.
- **Notes:** the Flutter session (`lib/models/session.dart`) carries a
  `userId` field — this is the **lookup key**, not the `partner_reference_id`
  itself (see `mobile/STATE_MANAGEMENT.md` → Session Seed).

## Which Backend Owns the Adobe Integration (multi-repo)

- **Owning backend:** this service (`base-ref-app/bff`) — it is the only
  backend surface in this app (single BFF, no microservices split).
- **This service's role:** would own the IMS token service, Retail API client,
  and (optionally) the Notify endpoint in full — there is no other backend to
  split responsibility with.
- **Notes:** this is not a multi-repo/multi-service setup; `base-ref-app/` is a
  single monorepo (`bff/` + `lib/`), so
  [`../shared/SURFACE_SCOPE.md`](../shared/SURFACE_SCOPE.md) records both
  surfaces as sharing the same repo root.
