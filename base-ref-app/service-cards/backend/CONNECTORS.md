# Connectors — Partner Ref App BFF

*Every outbound dependency this backend calls. The inbound surface belongs in
[`CONTRACTS.md`](./CONTRACTS.md).*

---

## 1. Overview

This backend has exactly one outbound dependency today: **MongoDB**, used for
partner-record storage (login credentials, admin management). There is no
outbound HTTP client dependency yet (no `axios`/`got`/`node-fetch` in
`bff/package.json`) — Node 20 (`engines.node: ">=20"` in `package.json`) has
native global `fetch`, so Adobe IMS/Retail API client code generated by the kit
may use native `fetch` without adding a new dependency. All future Adobe calls
must be backend-to-backend only, originating from this BFF — never from the
Flutter client.

## 3. Connector Details

### 1. MongoDB

- **Purpose:** stores `PartnerRecord` (id, displayName, optional maxClaims) for login + admin management.
- **Operations:**

  | Operation | Method / Path | Purpose |
  |---|---|---|
  | `connectMongo(uri)` | driver `MongoClient.connect()` | one-time connect at boot (`bff/src/db/mongo.ts`) |
  | `getDb().collection('partners_ref_app_partners').findOne/updateOne/find/deleteOne` | driver calls | CRUD via `bff/src/db/partnerStore.ts`'s `MongoPartnerStore` |

- **Auth & transport:** credentials embedded in the `MONGODB_URL` connection
  string (config key: `MONGODB_URL`, read in `bff/src/config.ts`). Default DB
  is whichever the URI specifies (`client.db()` with no explicit name).
- **Resilience:** none explicit — no retry/backoff wrapper around driver calls;
  relies on the driver's own reconnect behavior. Startup connection failure is
  caught and logged (non-fatal); per-request failures surface as thrown errors
  from `getDb()` if `connectMongo` never succeeded.
- **Error handling:** `index.ts`'s `start()` catches a startup connect failure
  and logs `event=startup.error reason=MONGO_CONNECT_FAILED` — the process
  still boots. Per-request Mongo errors (e.g. driver throwing) are not caught
  by a dedicated handler in routes today; they propagate as unhandled
  rejections in `admin.ts`/`auth.ts`'s async handlers (no global Express error
  middleware is registered in `index.ts`).
- **Unavailability posture:** login/admin requests fail (uncaught exception →
  Express default error response); `/health` degrades to `mongo: 'down'` but
  still returns `200`.

## 5. Adding a New Connector

- Add the client under a new `bff/src/adobe/` (or similarly named) directory,
  a sibling of `bff/src/db/`, matching that directory's single-purpose-module
  style (one file per responsibility: connect/init, plus a store or client
  class).
- Wire new env vars through `bff/src/config.ts`'s existing pattern
  (`validateConfig()` throws for boot-required vars; everything else is read
  with `?.trim() || undefined` and defaults gracefully) — see
  [`BUILD_CONFIG.md`](./BUILD_CONFIG.md) §3–5.
- Use native `fetch` (Node 20) unless a specific SDK is required; no HTTP
  client dependency needs to be added for simple REST calls.
- Log with the existing `event=<name> key=value` structured-log convention
  (`console.log`/`console.warn`/`console.error`), matching `auth.ts`/`admin.ts`.
- Add a Vitest test file alongside the new connector, following
  `auth/crypto.test.ts` / `auth/authService.test.ts`'s style (mock the driver
  or HTTP layer, not the service under test).
